# Step 1a.9 evidence: materializing implied relationships (D10)

- Date: 2026-11-21
- Step: 1a.9 of the Phase 1 execution plan
- Purpose: the evidence for decision D10 (how the implied relationships and elements of KerML 8.4.2 are materialized, ADR 0022), under the decision methodology (execution plan §2.5)

## Questions

1. **Where do implied relationships live?** ADR 0017 stores them in the graph, kept apart from the owned ones. Each file's fragment is lowered before resolution, though, and implied relationships depend on resolution across files (ADR 0019), so they cannot go into the lowered fragment. What should materialize them, and at what cost?
2. **Do the §7 budgets hold?** Those are re-resolve after a typical commit < 1 s on the server (1M elements), keystroke to diagnostics < 100 ms, and browser memory < 1 GB for a 50k-element working set.
3. **Identity.** 13 of the 80 `check…` constraints need implied *elements*: binding connectors, result parameters that are not written, `snapshots` features. These need an identity that the library UUIDs of step 1a.11 can use.

## Options

- **A, an elaborated graph:** a per-file query clones the lowered graph and adds the implied relationships as elements, with `Graph::add_implied_relationship` (ADR 0017).
- **B, records:** a per-file query returns the implied relationships as records (owner, kind, target) beside the graph.
- **C, an overlay:** a per-file query returns a small graph of the implied relationships only, with their owners and targets. It shares the lowered structure, which it does not copy. Readers would see the lowered structure and the overlay as one view.

## Method

A throwaway crate, `spike1a9`, outside the workspace, depends on the workspace's `sysml-semantics`, `sysml-model`, `sysml-syntax` and `sysml-corpus`, and on `salsa` 0.28.5.
- **The model.** The 36 KerML library files, and `generate`'s packages. Each package has 50 classifiers, each with a feature and an end feature, and 150 features typed by a classifier of its own package or of the next. Each package privately imports the next, around a ring. 50 packages give 62,631 elements; 1,300 give 1,005,131, both counting the libraries.
- **The shared work.** Both sizes first resolve, and compute the implied specializations and redefinitions of every element (`implied_generals`, `implied_redefinitions`, steps 1a.7 and 1a.8), which every option needs.
- **The options.** Each option's query is computed for every generated file. Option A's cross-file targets go in a side table, standing in for a cross-fragment endpoint, which `Graph` does not have. All three read the span-free `structure` (ADR 0019) and backdate.
- **The edits.** Each changes one file in the middle of the ring:
  - E1 retypes a feature;
  - E2 then adds white space only.

  After each edit, the edited file's query is computed (the editor), then every file's (the server after a commit).
- **Measurement.** A release build on the development machine (WSL2, 24 cores, 15 GB), one run per option, with a counting allocator for the memory each part adds, and `/usr/bin/time` for the peak.

## Results

### The resolution scaling bug

The first runs at 1M elements took 281 s to resolve, and 276 s after E1, with each option: the cost was resolution's, not materialization's. `visible_memberships` took all of a namespace's memberships, what its private imports bring included, and then kept the public ones. Around the ring of private imports, every package's visible memberships then depended on the next one's, in one fixpoint cycle of 1,300 packages that every edit reopened. KerML 8.3.2.4.5 (`membershipsOfVisibility`) evaluates only the public imports. Following it (PR #23, ADR 0020 decision 5a):

| 1M elements | Before | After |
|---|---|---|
| Resolution and implied generals | 281 s | 5.9 s |
| E1, the edited file | 276 s | 9 ms |
| E1, every file | 1.4 s | 264 ms |
| Shared memory | 1,909 MiB | 1,151 MiB |

The results below are on the fixed resolution.

### The options

| | 62,631 elements | 1,005,131 elements |
|---|---|---|
| Shared: resolution and implied generals | 0.33–0.37 s, 80 MiB | 5.9–6.6 s, 1,151 MiB |
| A, elaborated graph: materialize | 22 ms, +21 MiB | 0.88 s, +544 MiB |
| B, records: materialize | 10 ms, +1 MiB | 0.32 s, +21 MiB |
| C, overlay: materialize | 14 ms, +6 MiB | 0.47 s, +156 MiB |
| Peak memory: A / B / C | 120 / 101 / 104 MB | 1.95 / 1.45 / 1.54 GB |
| E1, the edited file: A / B / C | 5.2 / 4.5 / 4.4 ms | 9.3 / 8.3 / 8.8 ms |
| E1, every file: A / B / C | 12.8 / 11.7 / 12.0 ms | 264 / 265 / 265 ms |
| E2, the edited file: A / B / C | 0.8 / 1.0 / 1.1 ms | 4.2 / 4.5 / 4.7 ms |

- **Time does not separate the options.** An edit costs the same with each, about 9 ms for the edited file and 265 ms for every file at 1M elements: the cost is the shared queries'. All three backdate on a change of white space.
- **Memory does.**
  - A clones each file's whole graph to add the implied part, 544 MiB at 1M elements, which is 47% on top of the shared 1,151 MiB.
  - C stores only the implied part, but as full `Graph` elements, about 400 bytes each with their vectors, so 156 MiB.
  - B stores 20-byte records, 21 MiB.
  - At 50k elements, all three are well within the 1 GB browser budget.
- **Reading.** A and C give every reader one graph, or one view of the lowered structure and the overlay, with `Graph`'s accessors. B needs every reader, the derived properties, validation and interchange, to consult the records beside the graph.
- **Cross-file targets.** Most implied targets are in another file, usually a library: `Base::Anything`, `Performances::Performance`. `Graph`'s endpoints name elements of their own fragment, so A and C need a cross-fragment endpoint (in A in every graph, in C in the overlay only), and B holds `Global`s.
- **The budgets hold.** With any option, at 1M elements an edit re-resolves in 265 ms (< 1 s); at 50k, an edited file's queries take 5 ms (< 100 ms), and the peak is about 0.1 GB (< 1 GB).

//! D10 spike (step 1a.9): materializing implied relationships as an elaborated graph per file
//! (option A) or as records per file (option B), on a synthetic KerML model with the libraries.
use salsa::Setter;
use std::alloc::{GlobalAlloc, Layout, System};
use std::sync::atomic::{AtomicUsize, Ordering::Relaxed};
use std::sync::Arc;
use std::time::Instant;
use sysml_model::{Endpoint, FileId, Graph, Metaclass as M};
use sysml_semantics::{implied_generals, implied_redefinitions, lowered, structure, Database, Global, Project, SourceFile};
use sysml_syntax::Language;
use uuid::Uuid;

struct Counting;
static LIVE: AtomicUsize = AtomicUsize::new(0);
unsafe impl GlobalAlloc for Counting {
    unsafe fn alloc(&self, l: Layout) -> *mut u8 {
        LIVE.fetch_add(l.size(), Relaxed);
        System.alloc(l)
    }
    unsafe fn dealloc(&self, p: *mut u8, l: Layout) {
        LIVE.fetch_sub(l.size(), Relaxed);
        System.dealloc(p, l)
    }
}
#[global_allocator]
static A: Counting = Counting;

fn mib() -> f64 {
    LIVE.load(Relaxed) as f64 / (1024.0 * 1024.0)
}

/// `packages` files: classifiers, features typed by them, and nested features, so that every
/// element has implied specializations (Anything, things) and some have implied redefinitions.
fn generate(packages: usize, classifiers: usize, features: usize) -> Vec<String> {
    (0..packages)
        .map(|i| {
            let a = (i + 1) % packages;
            let mut t = format!("package P{i} {{\n    private import P{a}::*;\n");
            for k in 0..classifiers {
                t.push_str(&format!("    classifier C{i}_{k} {{ feature x; end feature e; }}\n"));
            }
            for k in 0..features {
                let j = if k % 2 == 0 { i } else { a };
                t.push_str(&format!("    feature f{i}_{k} : C{j}_{};\n", k % classifiers));
            }
            t.push_str("}\n");
            t
        })
        .collect()
}

// ---- option A: the elaborated graph ----

/// A file's fragment with its implied relationships as elements, kept apart (ADR 0017). A target
/// in another file is a remote endpoint: here a side table, as a Graph has no such endpoint yet.
#[derive(Clone)]
pub struct Elaborated {
    graph: Arc<Graph>,
    remote: Vec<(u32, u32, u32)>,
}
impl PartialEq for Elaborated {
    fn eq(&self, o: &Self) -> bool {
        self.remote == o.remote && self.graph.same_structure(&o.graph)
    }
}
impl Eq for Elaborated {}

#[salsa::tracked(returns(ref))]
fn elaborated(db: &dyn salsa::Database, project: Project, file: SourceFile) -> Elaborated {
    let l = structure(db, file);
    let mut g: Graph = l.graph().clone();
    let mut remote = Vec::new();
    let mut n = g.len() as u128;
    let n0 = g.len();
    for i in 0..n0 {
        let x = sysml_model::ElementIx::from_index(i);
        let mut add = |g: &mut Graph, kind: M, target: Global| {
            n += 1;
            let r = g.add(kind, Uuid::from_u128(n)).unwrap();
            g.add_source(r, Endpoint::Element(x));
            if target.file == file {
                g.add_target(r, Endpoint::Element(target.ix()));
            } else {
                remote.push((r.index() as u32, target.file.file_id(db).0, target.index));
            }
            g.add_implied_relationship(x, r);
        };
        for imp in implied_generals(db, project, file, i as u32) {
            add(&mut g, imp.kind, imp.general);
        }
    }
    Elaborated { graph: Arc::new(g), remote }
}

// ---- option C: an overlay on the shared lowered structure ----

/// The implied part of a file only: a graph of the implied relationship elements, with each one's
/// owner (an element of the lowered fragment, which stays shared) and its target (in this file
/// or another). Readers would see the lowered structure and this overlay as one view.
#[derive(Clone)]
pub struct Overlay {
    base: sysml_semantics::Structure,
    implied: Graph,
    owner: Vec<u32>,
    target: Vec<(u32, u32)>,
}
impl PartialEq for Overlay {
    fn eq(&self, o: &Self) -> bool {
        self.owner == o.owner && self.target == o.target && self.implied.same_structure(&o.implied)
    }
}
impl Eq for Overlay {}

#[salsa::tracked(returns(ref))]
fn overlay(db: &dyn salsa::Database, project: Project, file: SourceFile) -> Overlay {
    let base = structure(db, file).clone();
    let mut implied = Graph::new();
    let (mut owner, mut target) = (Vec::new(), Vec::new());
    let mut n = 0u128;
    for i in 0..base.graph().len() as u32 {
        for imp in implied_generals(db, project, file, i) {
            n += 1;
            implied.add(imp.kind, Uuid::from_u128(n)).unwrap();
            owner.push(i);
            target.push((imp.general.file.file_id(db).0, imp.general.index));
        }
    }
    Overlay { base, implied, owner, target }
}

// ---- option B: records ----

#[salsa::tracked(returns(ref))]
fn records(db: &dyn salsa::Database, project: Project, file: SourceFile) -> Vec<(u32, M, Global)> {
    let l = structure(db, file);
    let mut out = Vec::new();
    for i in 0..l.graph().len() as u32 {
        for imp in implied_generals(db, project, file, i) {
            out.push((i, imp.kind, imp.general));
        }
    }
    out
}

fn main() {
    let packages: usize = std::env::args().nth(1).and_then(|a| a.parse().ok()).unwrap_or(50);
    let option = std::env::args().nth(2).unwrap_or_else(|| "A".into());
    let texts = generate(packages, 50, 150);
    let corpus = sysml_corpus::Corpus::load().unwrap();
    let mut db = Database::default();
    let mut files: Vec<SourceFile> = corpus
        .sources()
        .filter(|s| s.language == sysml_corpus::Language::KerML)
        .map(|s| s.text.clone())
        .chain(texts.iter().cloned())
        .enumerate()
        .map(|(i, t)| SourceFile::new(&db, FileId(i as u32), format!("f{i}.kerml"), Language::KerML, t))
        .collect();
    let user = files.len() - packages;
    let project = Project::new(&db, files.clone());
    let base = mib();
    // Resolution and the implied generals both options need.
    let t = Instant::now();
    let mut elements = 0usize;
    for f in &files {
        elements += lowered(&db, *f).graph.len();
        let l = lowered(&db, *f);
        for i in 0..l.graph.len() as u32 {
            let _ = implied_generals(&db, project, *f, i);
            let _ = implied_redefinitions(&db, project, *f, i);
        }
    }
    let shared = t.elapsed();
    let shared_mem = mib() - base;
    let run = |db: &Database| -> usize {
        files[user..]
            .iter()
            .map(|f| match option.as_str() {
                "A" => elaborated(db, project, *f).graph.len(),
                "C" => overlay(db, project, *f).implied.len() + overlay(db, project, *f).base.graph().len() * 0,
                _ => records(db, project, *f).len(),
            })
            .sum()
    };
    let before = mib();
    let t = Instant::now();
    let size = run(&db);
    let first = t.elapsed();
    let own_mem = mib() - before;
    // E1: retype a feature; E2: white space.
    let i = user + packages / 2;
    let text = files[i].text(&db).clone();
    let e1 = text.replacen(": C", ":C", 1).replacen(&format!("C{}_0;", packages / 2), &format!("C{}_1;", packages / 2), 1);
    let mut times = Vec::new();
    let e2 = format!("{e1} ");
    for edit in [e1, e2] {
        // The editor: the edited file's implied relationships only.
        files[i].set_text(&mut db).to(edit.clone());
        let t = Instant::now();
        match option.as_str() {
            "A" => { let _ = elaborated(&db, project, files[i]).graph.len(); }
            "C" => { let _ = overlay(&db, project, files[i]).implied.len(); }
            _ => { let _ = records(&db, project, files[i]).len(); }
        }
        let one = t.elapsed();
        // The server after a commit: every file's.
        let t = Instant::now();
        run(&db);
        times.push((one, t.elapsed()));
    }
    let _ = &mut files;
    println!(
        "option {option}: {elements} elements; resolution and implied generals {:?}, {:.0} MiB; \
         materialize {:?} ({size}), {:.0} MiB; E1 file/all {:?}, E2 file/all {:?}",
        shared, shared_mem, first, own_mem, times[0], times[1]
    );
}
